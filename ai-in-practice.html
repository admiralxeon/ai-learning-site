AI in practice: from a model to a product

This module is written in ASD-STE100 Simplified Technical English, at approximately 80% compliance. Read Module 3, Machine learning and Module 5, Generative AI before you read this module. The other modules tell you how a model works. This module tells you how to make a model work reliably for real users, every day. Names with a dotted line are technical names. Put the pointer on a name to see its definition.

After this module, you can:
  • Prepare data without data leakage, and compare models with a baseline.
  • Test models fairly with cross-validation.
  • Release a model safely and monitor it for drift.
  • Test LLM applications with an evaluation set, and use agents safely.

Scope

This module gives a description of the work that changes a model into a product.

It tells you:

  • The steps of the life of an AI system.
  • How to prepare data, and how to prevent data leakage.
  • Why each model needs a baseline.
  • How to test a model fairly with cross-validation.
  • How to put a model into use, and how to monitor it.
  • How to build, test, and control an application that uses an LLM.
  • How to use AI agents safely.
2

From a model to a product

In a project notebook, a model is finished when its test result is good. In a product, that is only the start. Real users send new data each day. The world changes. The model must stay correct, fast, safe, and affordable.

The life of an AI system is a loop, not a line. Refer to Figure 1.

Note

In 2015, Google engineers wrote that in real ML systems, the model code is only a small part of all the code. The data pipelines, tests, monitoring, and settings around it are much larger. Thus plan time for all six steps, not only for training.

3

Prepare the data

Real data is never clean. Before training, do these checks. Refer also to Module 3, Section 4.

Missing values

Some examples do not have a value for a feature. For example, the camera did not measure the weight of some mangoes. You can:

  • Remove the examples with missing values, if there are only a few.
  • Put the median of the feature in the empty places. We call this imputation.
  • Add a feature "value is missing" (yes or no). Sometimes the fact that a value is missing is useful information.

Categories

A model can use only numbers. A feature such as "type of mango" contains words. One-hot encoding changes each category into its own column with 0 or 1:

Type of mangoAlphonsoKesarTotapuri
Alphonso100
Kesar010
Totapuri001

Do not change categories into 1, 2, and 3. The model would think that Totapuri is "more" than Alphonso.

Other checks

  • Duplicates. Remove examples that occur two times.
  • Units. Make sure that all values use the same unit, for example grams and not grams and kilograms together.
  • Scale. Standardize features that have very different sizes. Refer to Module 2, Section 5.

Data leakage

Data leakage occurs when the model learns from information that it will not have in real use. The test result is excellent, but the model fails with real users.

Warning

Examples of data leakage: (1) A feature "customer complained" helps to predict damaged mangoes, but a complaint occurs only after the sale. (2) The same mango is photographed two times, and one photograph goes into the training set and one into the test set. (3) You calculate the mean for standardization with all the data, before you divide it. Always divide the data first. Then calculate everything from the training set only.

Procedure: check for data leakage

  1. For each feature, ask: "Will this value be available at the time of the prediction?" If not, remove it.
  2. Make sure that copies of the same item cannot go into two different sets. Divide by item, by customer, or by date.
  3. Divide the data before you clean, scale, or select features.
  4. If a result looks too good, for example 100% accuracy, look for leakage first.
4

Start with a baseline

A baseline is a very simple method that you compare your model with. If your model is not better than the baseline, it is not useful.

TaskA usual baseline
ClassificationAlways predict the most frequent category.
RegressionAlways predict the mean of the training labels.
Forecast for tomorrowPredict the same value as today.
Any taskA simple rule that an expert writes, or the result of a person.

Example: in the spam data of Project 3, 4,825 of 5,572 messages are not spam. A "model" that always says "not spam" is 86.6% accurate. Thus a real model with 90% accuracy is only a small improvement. The model in Project 3 has 99%, so it is much better than the baseline. But also remember: the baseline finds zero spam. Its recall is 0%.

Note

Start each project with the simplest model that can work. Use a complex model only if it is clearly better. A simple model is cheaper, faster, and easier to explain.

5

Test fairly with cross-validation

With one division of the data, the result depends on luck: some test sets are easier than others. Cross-validation gives a more reliable result. Refer to Figure 2.

  1. Divide the training data into 5 equal parts. We call each part a fold.
  2. Train the model on 4 parts. Test it on the fifth part.
  3. Do this 5 times. Each time, use a different part for the test.
  4. Calculate the mean and the spread of the 5 results.

Hyperparameters

Training finds the weights. But a person selects some settings before training, for example the learning rate, the number of layers, or the number of groups in k-means. We call these settings hyperparameters. To select them, try different values, and compare the cross-validation results. Never use the final test set for this. Refer to Module 3, Section 4.

6

Put a model into use

Deployment makes the model available to its users. There are three usual ways:

WayHow it worksGood for
BatchThe model makes many predictions at one time, for example each night.Reports, recommendations, risk lists.
Online (server)An app sends one request. The model answers in less than one second.Chat AI, search, fraud checks during a payment.
On the deviceThe model runs on a phone, a camera, or a machine.Work without internet, privacy, very fast answers. The mango checker at the sorting table.

Important measurements in use

  • Latency: the time for one answer. A sorting machine needs an answer in milliseconds.
  • Cost: the price of computers or of an AI service for each prediction.
  • Availability: what occurs when the model or the internet does not work. Always have a fallback, for example a person or a simple rule.

Procedure: release a new model safely

  1. Give each model a version number. Keep the old version.
  2. Run the new model in shadow mode first: it makes predictions on real data, but nobody uses them. Compare them with the current system.
  3. Give the new model to a small part of the users, for example 5%. Compare the results of the two groups. We call this an A/B test.
  4. If the results are good, give the new model to all users.
  5. If a problem occurs, go back to the old version immediately.
7

Monitor the model

A model does not change after training. But the world changes. Then the model becomes less accurate, often without an error message. There are two types of change:

  • Data drift: the inputs change. Example: a new type of mango, a new camera, or summer light in place of winter light.
  • Concept drift: the meaning of the correct answer changes. Example: spam senders change their words, so old spam words do not work any more.

What to monitor

  • The results that you can check: a sample of predictions each week, checked by a person.
  • The inputs: are the means and the distributions still similar to the training data?
  • The outputs: did the percentage of "damaged" predictions suddenly change?
  • Complaints, latency, and cost.

Set a limit for each measurement. If a value goes past the limit, the system sends an alert, and a person examines the problem. Often the solution is to collect new data and train the model again. To build this monitoring loop in code, do Project 8.

Try it

Keep a model accurate for 18 months

After month 6, a new type of mango comes to the farm, and the recall of the checker starts to decrease. Turn monitoring on or off, and change the alert limit. Find a good balance between the recall and the cost of training again.

Project: the mango checker · Part 7 of 9

One year later

The mango checker now works on 12 farms. One year after the first release, the team looks at its monitoring dashboard:

  • Each week, a worker checks 200 random mangoes from each box. The recall for damaged mangoes was 97%. In the last month, it decreased to 88%.
  • The cause: a new camera on three farms. Its pictures are brighter. This is data drift.
  • The team collects 1,500 photographs from the new cameras, trains the model again, and tests it in shadow mode for one week. Then they release version 2.1. The recall is 96% again.
  • The farmers' chatbot from Part 5 now answers 3,000 questions each day. The team tests each new prompt on a set of 50 questions before they change it.
Think: why did the team find the problem only through the weekly check, and not through an error message?

The model did not stop. It continued to give answers, but more of them were wrong. A model that gets worse looks the same as a good model. Only a check of real results shows the problem.

8

Build with large language models

Many AI products today do not train a model. They use an LLM from a company, and add a prompt, documents (RAG), and tools. Refer to Module 5, Section 8. This is fast, but it needs its own tests and controls.

Test an LLM application

An LLM gives different answers each time, and a small change in the prompt can change many answers. Thus make an evaluation set: a fixed list of example questions with good answers. Use it like the test in Project 6.

  1. Collect 50 to 200 real questions, including difficult ones and questions that the system must refuse.
  2. For each question, write what a good answer must contain.
  3. Each time you change the prompt, the documents, or the model, run all the questions again.
  4. Compare the score with the previous version. Do not release a version with a lower score.

Some teams use a second LLM to grade the answers. This saves time, but check a sample of its grades by hand. The grader can also make errors.

Guardrails

Guardrails are checks around the model:

  • Input checks: remove private data, and stop requests that are not allowed.
  • Output checks: check the format, check that the answer uses the documents, and stop harmful content.
  • Defense against prompt injection: treat text from web pages and documents as data, not as instructions. Refer to Module 5, Section 9.

Calculate the cost

AI services usually charge for each token, and output tokens cost more than input tokens. Example, with prices that are only for this calculation: input costs ₹250 for 1 million tokens, and output costs ₹1,000 for 1 million tokens.

one answer = 2,000 input tokens × ₹250 ÷ 1,000,000 + 300 output tokens × ₹1,000 ÷ 1,000,000 = ₹0.50 + ₹0.30 = ₹0.80

For 3,000 answers each day, the cost is approximately ₹2,400 each day. RAG adds input tokens, because the found text goes into each prompt. Thus send only the parts of the documents that are necessary.

Agents in practice

An AI agent works in a loop. It plans a step, uses a tool, looks at the result, and plans the next step. Refer to Figure 3.

Workflow or agent?

If the steps are always the same, use a fixed workflow: step 1, then step 2, then step 3. It is cheaper, faster, and easier to test. Use an agent only when the steps must change for each task.

Rules for safe agents

  • Give the agent only the tools and the permissions that it needs. For example, it can read the calendar, but it cannot delete events.
  • Let a person approve each important action. Refer to Module 6, Section 5.
  • Set a maximum number of steps and a maximum cost for each task.
  • Keep a record of each step, so that you can find the cause of an error.
  • Test the agent with an evaluation set, as for each LLM application.
10

Summary

  • The model is only one step in the life of an AI system. Plan for data, evaluation, deployment, and monitoring.
  • Clean the data, and look for data leakage. Divide the data before you prepare it.
  • Compare each model with a simple baseline.
  • Cross-validation gives a more reliable result than one test. Select hyperparameters with it, not with the final test set.
  • Release new models step by step: shadow mode, a small A/B test, then all users. Keep the old version.
  • Monitor real results. Data drift and concept drift make a model worse without an error message.
  • Test LLM applications with an evaluation set, use guardrails, and calculate the cost.
  • Use agents only when necessary, with limited tools, limits, records, and human approval.

12

Technical names

These names are not in the STE dictionary. STE lets you use technical names that are necessary for the subject.

A/B test
A test that gives a new version to a small group of users and compares their results with the other users.
Baseline
A very simple method that gives a minimum result to compare with.
Concept drift
A change in the relation between the inputs and the correct answer.
Cross-validation
A method that trains and tests k times, each time on a different part of the data.
Data drift
A change in the input data after deployment.
Data leakage
Training data that contains information that is not available in real use, or that comes from the test set.
Deployment
The work that makes a trained model available to its users.
Evaluation set
A fixed set of example inputs with good answers, to test each new version.
Guardrail
A check before or after the model that stops unsafe inputs and outputs.
Hyperparameter
A setting that a person selects before training.
Imputation
To fill missing values with an estimate, for example the median.
Latency
The time between a request and its answer.
One-hot encoding
A method that changes one feature with categories into columns with 0 or 1.
Shadow mode
A test in which a new model makes predictions on real data that nobody uses yet.
