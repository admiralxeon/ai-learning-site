Capstone: build and ship an AI product

The capstone is the final work of the AI Engineer track. You build a real AI product from the start to the end, put it on GitHub, and grade it with a rubric. A passed capstone is necessary for the AI Engineer certificate. It is also the most important item of your portfolio.

1

About the capstone

  • Time: approximately 15 to 25 hours, in 4 weeks.
  • Start: make your plan with the worksheet in Module 6, Section 8. That plan is part 1 of the capstone. This page is part 2: the build.
  • Select one option: an ML service (Option A) or a RAG application (Option B).
  • Work alone or in a team of two. In a team, each person must be able to explain all the code.
  • Grading: you grade your work with the rubric in Section 6. For a certificate that other people can check, a reviewer also grades it. Refer to the certificate page.
Caution

Use public data or data that you have permission to use. Do not put personal data, passwords, or API keys into the repository. Refer to Module 8, Section 10.

2

Option A: an ML service

Train a model on a real data set, and serve it as a tested API, as in Module 8 and Project 9.

Minimum requirements

  • A real data set of at least 1,000 rows, for example from Kaggle, the UCI Machine Learning Repository, or data.gov.in.
  • A baseline and at least one better model, compared with cross-validation. Refer to Module 7, Section 5.
  • No data leakage: a written check of each feature. Refer to Module 7, Section 3.
  • An API with input checks, a health address, and the model version in each answer.
  • Tests, including a quality gate, that run in a CI pipeline.
  • A Dockerfile, and a drift check on new data, as in Project 8.

Ideas: predict late deliveries for a shop, find damaged products from sensor data, predict the demand of a product (refer to Forecasting), or sort support emails by subject.

3

Option B: a RAG application

Build an assistant that answers questions from a set of documents, with sources, as in Module 9.

Minimum requirements

  • At least 20 public documents, for example the rules of your college, the FAQ of a government scheme, or the manuals of a product.
  • Chunks, an embedding model or TF-IDF, and a search that you can explain.
  • Answers that cite their sources, and say "I do not know" when the sources do not contain the answer.
  • An evaluation set of at least 30 questions: a retrieval test (recall at k) and a judge with reference answers.
  • Guardrails: input checks, output checks, and a limit on cost. Refer to Module 9, Section 7.
  • A simple interface: a web page, a chat in Streamlit or Gradio, or a command-line program.

Ideas: a help desk for new students, an assistant for farmers in a local language, or a search tool for the documents of a small company.

6

Rubric and self-assessment

For each criterion, select the level that agrees with your work. Be honest: a reviewer uses the same rubric. To pass, you need 70% or more, no criterion at level 1, and a complete checklist.

1. Problem and users
2. Data and baseline
3. Model or pipeline
4. Evaluation
5. Engineering
6. Responsible AI
7. Communication
7

Peer review

A second opinion makes your grade more reliable, and it is good practice for code review at work.

  1. Give your repository and this page to a friend or a colleague who also studies the course.
  2. Ask them to run your project with only the README, and to grade it with the rubric.
  3. Compare their grades with yours. Talk about each criterion with a difference of 2 levels or more.
  4. Improve the weakest criterion, and grade again.
