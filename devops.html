DevOps for AI: build, ship, and run an AI product

This module is written in ASD-STE100 Simplified Technical English, at approximately 80% compliance. Read Module 7, AI in practice before you read this module. Module 7 tells you what a model needs in real use. This module tells you how teams build, test, release, and operate the software around the model, every day, without errors. You will change the mango checker into a small web service, put it in a container, and test it automatically. Names with a dotted line are technical names. Put the pointer on a name to see its definition.

After this module, you can:
  • Keep versions of code, data, models, and prompts.
  • Serve a model as an API and package it in a container.
  • Build a CI/CD pipeline with quality gates.
  • Observe a service in production and protect its secrets.

Part of

AI Engineer

1

Scope

This module gives a description of the engineering work that makes an AI product reliable.

It tells you:

  • What DevOps is, and what MLOps and LLMOps add for AI.
  • How to keep versions of code, data, models, and prompts.
  • How to serve a model as an API, and how to put it in a container.
  • How automatic tests and a CI/CD pipeline release changes safely.
  • How to run the service in the cloud, and how to observe it.
  • How to keep secrets and the system safe.
Note

The code in this module is tested with Python, scikit-learn 1.9, and FastAPI. To run it, you need Python on your computer. Docker is necessary only for Section 6.

2

What DevOps is

In the past, one team wrote the software (development) and a different team ran it on the servers (operations). The two teams frequently blamed each other for problems, and releases were slow and risky. DevOps joins the two types of work.

  • Small changes, frequently. A small change is easy to test, and easy to remove if it is wrong.
  • Automation. Machines do the tests, the builds, and the releases. People do not do the same steps by hand each time.
  • Fast feedback. The team sees immediately if a change causes a problem, in the tests or in production.
  • Shared responsibility. The team that builds the service also helps to operate it.

The work is a loop with no end. Refer to Figure 1.

Teams frequently measure DevOps with four numbers: how frequently they release, how long a change takes to reach users, how many releases cause a problem, and how long it takes to repair a problem.

3

MLOps and LLMOps: what is different for AI

Usual software changes only when a person changes the code. An AI system can also change when the data changes, and it can become worse without a change in the code. Refer to Module 7, Section 7. Thus AI teams add more work to DevOps.

PracticeWhat it adds
DevOpsVersions of code, automatic tests, automatic releases, monitoring of the servers.
MLOpsVersions of data and models, automatic model tests, a model registry, monitoring for drift, and automatic training again.
LLMOpsVersions of prompts, evaluation sets that run in the pipeline, guardrails, and monitoring of token cost and answer quality.

A team does not need all of this on the first day. Start with the basics, and add more when the product grows:

  1. Level 0: a person trains the model in a notebook and copies the file to a server by hand.
  2. Level 1: the code is in Git, the tests are automatic, and a pipeline releases the service.
  3. Level 2: the pipeline also trains and tests new models, and the monitoring starts training again when drift occurs.
4

Keep a version of everything

If a problem occurs, you must know exactly what changed, and you must be able to go back. Thus keep a version of each part of the system.

PartUsual tool
Code and settingsGit, with a shared copy on GitHub or GitLab.
DataA data versioning tool, for example DVC, or dated copies in cloud storage that nobody changes.
ModelsA model registry: each model with its version, its training data, and its test results.
PromptsIn Git, as files, the same as code.
LibrariesA requirements file with exact version numbers.

Procedure: make a change with Git

  1. Make a new branch for the change, for example git switch -c new-threshold.
  2. Make the change. Save it in small steps with git commit. Write a short message that tells why.
  3. Send the branch to GitHub, and open a pull request.
  4. The automatic tests run. Another person reviews the change.
  5. When the tests pass and the review is good, join the branch into main. The pipeline then releases it.

5

Serve the model as an API

An app, a website, or a machine on the sorting line must ask the model for predictions. The usual way is an API: the program sends a request with the features, and the service sends back the prediction. Refer to Module 7, Section 6.

Step 1: train and save the model

This program makes example data for 2,000 mangoes, trains a model, and saves it to a file with a version number.

train.py
import json
import joblib
import numpy as np
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import recall_score
from sklearn.model_selection import train_test_split

# 1. Make example data: 2,000 mangoes with three features each.
rng = np.random.default_rng(0)
n = 2000
weight = rng.normal(250, 40, n)        # grams
firmness = rng.normal(6, 1.5, n)       # 0 (soft) to 10 (hard)
spots = rng.poisson(1.5, n)            # dark spots on the skin
damaged = ((spots >= 4) | (firmness < 3.5)).astype(int)
wrong = rng.random(n) < 0.01           # 1% of the labels are wrong, as in real data
damaged = damaged ^ wrong
X = np.column_stack([weight, firmness, spots])

# 2. Divide the data, train the model, and measure it.
X_train, X_test, y_train, y_test = train_test_split(
    X, damaged, test_size=0.2, random_state=1, stratify=damaged)
model = RandomForestClassifier(n_estimators=100, random_state=1)
model.fit(X_train, y_train)
recall = recall_score(y_test, model.predict(X_test))
print("Recall for damaged mangoes:", round(recall, 3))

# 3. Save the model and its results, with a version number.
joblib.dump(model, "model.joblib")
with open("model_info.json", "w") as f:
    json.dump({"version": "1.0.0", "recall": round(recall, 3)}, f)

Step 2: make the web service

This program uses FastAPI. It loads the model one time when it starts. It has two addresses: /health tells if the service works, and /predict gives a prediction. The Mango class checks each input. A weight of −5 grams is refused.

app.py
import json
import joblib
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI(title="Mango checker")
model = joblib.load("model.joblib")
with open("model_info.json") as f:
    info = json.load(f)


# The input that the API accepts. Values outside these limits are refused.
class Mango(BaseModel):
    weight_g: float = Field(gt=0, lt=1000)
    firmness: float = Field(ge=0, le=10)
    spots: int = Field(ge=0, le=100)


@app.get("/health")
def health():
    return {"status": "ok", "model_version": info["version"]}


@app.post("/predict")
def predict(mango: Mango):
    p = model.predict_proba([[mango.weight_g, mango.firmness, mango.spots]])[0][1]
    return {"damaged": bool(p >= 0.5), "probability": round(float(p), 3),
            "model_version": info["version"]}

Step 3: run it

Put the two files and requirements.txt (refer to Section 6) in one folder. Then type these commands in a terminal:

Terminal
pip install -r requirements.txt
python train.py
uvicorn app:app --port 8000

The training prints Recall for damaged mangoes: 0.98. Then open http://localhost:8000/docs in a browser. FastAPI makes a page where you can send test requests. A request with {"weight_g": 240, "firmness": 2, "spots": 6} gives {"damaged": true, "probability": 1.0, "model_version": "1.0.0"}.

Note

Each answer contains the model version. When a user reports a wrong answer, the team knows immediately which model gave it.

6

Package it in a container

"It works on my computer" is a usual problem. The server has a different version of Python or of a library, and the service fails. Two solutions work together:

  • Exact versions. A requirements file gives the exact version of each library.
  • A container. It packs the program with everything that it needs. The same container runs the same way on your computer, on the test server, and in production.
requirements.txt
fastapi==0.135.1
uvicorn==0.41.0
scikit-learn==1.9.0
numpy==2.4.6
joblib==1.5.3
httpx==0.28.1
pytest==9.1.1

A Dockerfile gives the steps to build the container image:

Dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py model.joblib model_info.json ./
EXPOSE 8000
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]

Build the image with a version tag, and start it:

Terminal
docker build -t mango-checker:1.0.0 .
docker run -p 8000:8000 mango-checker:1.0.0

Environments

Teams usually have three copies of the system. The same container image goes through all three:

  1. Development: on the computer of the developer.
  2. Staging: a copy of production, for the last tests. It does not have real users.
  3. Production: the system that real users use.

7

Test and release automatically

CI/CD means continuous integration and continuous delivery. Each change goes through the same automatic steps, called a pipeline. Refer to Figure 2.

Tests for an AI service

Test more than the code. These tests check the API, the input checks, and the quality of the model:

test_app.py
from fastapi.testclient import TestClient
from app import app, info

client = TestClient(app)


def test_health():
    assert client.get("/health").status_code == 200


def test_good_mango():
    r = client.post("/predict", json={"weight_g": 260, "firmness": 7, "spots": 0})
    assert r.json()["damaged"] is False


def test_damaged_mango():
    r = client.post("/predict", json={"weight_g": 240, "firmness": 2, "spots": 6})
    assert r.json()["damaged"] is True


def test_bad_input_is_refused():
    r = client.post("/predict", json={"weight_g": -5, "firmness": 7, "spots": 0})
    assert r.status_code == 422


def test_model_is_good_enough():
    assert info["recall"] >= 0.90

Run them with the command pytest. The last test is a quality gate: if a new model has a recall of less than 90%, the test fails, and the pipeline does not release that model.

The pipeline file

GitHub Actions runs this pipeline automatically for each pull request and for each change to main. Put the file in the folder .github/workflows.

.github/workflows/ci.yml
name: Test and build
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test-and-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: python train.py
      - run: pytest
      - run: docker build -t mango-checker:${{ github.sha }} .

For an LLM application, add the evaluation set to the pipeline. Refer to Module 7, Section 8. A change to a prompt is then tested the same as a change to code.

8

Run it in the cloud

Most teams rent servers from a cloud company in place of buying them. There are different levels of service. Refer to the table.

OptionYou manageGood for
Virtual machineThe operating system, the container, the updates.Full control, special hardware.
Container serviceOnly the container. The cloud starts and stops copies.Most web services and APIs.
KubernetesA cluster of many containers and services.Large systems with many services and a platform team.
Serverless functionsOnly the code of one function.Small tasks that run sometimes. Not for large models.
Managed AI serviceOnly the prompts and the data. The company runs the model.LLM applications. Refer to Module 5.

Scale and cost

  • Autoscaling: the cloud starts more copies of the container when there are many requests, and stops them when there are few. A load balancer divides the requests between the copies.
  • GPUs are expensive. Use them only for models that need them. A small model like the mango checker runs well on a usual processor.
  • Cost alerts: set a monthly budget and an alert. A mistake in autoscaling can cost much money in one night.

Infrastructure as code

Do not make the servers, the networks, and the databases by hand in the web console of the cloud. Write them in files, for example with Terraform. We call this infrastructure as code. The files go into Git, so a change to the servers gets a review, and you can make the same system again after a disaster.

Observe the system in production

Module 7 tells you how to monitor the quality of the model. The service around the model also needs monitoring. We call the ability to see what occurs inside a running system observability. It uses three types of data. Refer to Figure 3.

Set clear targets

A service level objective (SLO) is a target that the team agrees on. Examples:

  • Availability: 99.9% of the requests are successful each month. In a month of 30 days, this allows 30 × 24 × 60 × 0.001 = 43.2 minutes without service.
  • Latency: 95% of the answers come in less than 100 ms. We call this the p95 latency. Use the p95, not the mean. The mean hides the slow answers that make users angry.

Procedure: when an alert comes

  1. Confirm the problem on the dashboard. Tell the team that you are working on it.
  2. Stop the damage first. If a new release caused the problem, do a rollback to the previous version.
  3. Find the cause with the logs and the traces.
  4. Repair the cause. Release the repair through the normal pipeline.
  5. Write a short report without blame: what occurred, why, and what change prevents it next time. We call this a postmortem.

Project: the mango checker · Part 8 of 9

Forty farms, one service

The mango checker is now a web service in the cloud. Forty farms send it 2 million requests each day. The team uses a pipeline for each change.

  • The team releases model version 2.2. All tests pass. In the canary release, the dashboard shows that the p95 latency increases from 40 ms to 600 ms. The sorting lines on two farms become slow.
  • The person on call does a rollback to version 2.1 in two minutes. Only the farms in the canary group were affected, for 20 minutes.
  • The postmortem finds the cause: version 2.2 is a much larger model. The team adds a load test to the pipeline. Now a model that is too slow cannot pass the pipeline.
Think: all the tests passed. Why did the problem still occur, and why was the damage small?

The tests checked the accuracy, but not the speed. The canary release showed the problem with real traffic, but only to 5% of the users. The fast rollback stopped the damage. Each layer of protection catches some problems that the other layers miss.

Security and secrets

A secret is a password, an API key, or a token. Many security problems start with a secret in the wrong place.

Warning

Never put a secret in the code or in Git. Automatic programs search public repositories for keys all the time, and they can use a key minutes after it is published. If a secret gets into Git, change the secret immediately. To remove it from the code is not sufficient, because the history of Git still contains it.

  • Keep secrets in a secret manager or in the secret settings of the pipeline. The program reads them from environment variables when it starts.
  • Give the least access. Each service gets only the permissions that it needs. Refer to Module 7, Section 9.
  • Scan automatically. Add a secret scan and a check of the libraries for known security problems to the pipeline.
  • Check all inputs. The API refuses values that are not possible, as the Mango class does. For LLM applications, also defend against prompt injection. Refer to Module 5, Section 9.
  • Protect personal data in logs too. Do not write names, phone numbers, or full prompts with private data into the logs. Refer to Module 6, Section 4.
11

Summary

  • DevOps joins development and operations: small changes, automation, fast feedback, and shared responsibility.
  • MLOps adds versions of data and models, model tests, and training again. LLMOps adds prompt versions, evaluation sets, and cost monitoring.
  • Keep a version of code, data, models, prompts, and libraries. Make changes on a branch, with a pull request and a review.
  • Serve the model as an API. Check each input, and send the model version with each answer.
  • Pin the library versions, and put the service in a container. The same image goes to development, staging, and production.
  • A CI/CD pipeline tests and releases each change. Quality gates stop bad models. A canary release tests with real traffic.
  • Use logs, metrics, and traces. Set SLOs. When a problem occurs, roll back first, then find the cause.
  • Never put secrets in code. Give the least access, and scan the code automatically.

Technical names

These names are not in the STE dictionary. STE lets you use technical names that are necessary for the subject.

API
Application programming interface: a defined way for one program to ask another program for data or an action.
Autoscaling
The automatic change of the number of running copies of a service, to agree with the number of requests.
Branch
A separate line of work in Git. You join it into the main branch after review.
Canary release
A release of a new version to a small part of the users first.
CI/CD
Continuous integration and continuous delivery: each change is tested, packaged, and released automatically.
Container
A package that contains a program and everything that it needs to run.
DevOps
A way of working in which the same team builds, tests, releases, and operates software, with much automation.
Dockerfile
A text file with the steps to build a container image.
Git
A version control system that keeps each change to the files.
Infrastructure as code
A method in which files describe the servers and networks, so they can be reviewed, versioned, and made again.
Kubernetes
A system that runs many containers on many servers and manages them automatically.
LLMOps
MLOps for applications that use large language models: prompt versions, evaluation sets, guardrails, and cost monitoring.
MLOps
DevOps for machine learning: versions of data and models, automatic model tests, and training again.
Model registry
A store for trained models, with their versions, data, test results, and status.
Observability
The ability to know what occurs inside a running system from its logs, metrics, and traces.
Pipeline
A sequence of automatic steps that each change goes through.
Pull request
A request to join the changes of a branch into the main branch, with review and automatic tests.
Quality gate
A check in a pipeline that a release must pass, for example a minimum recall.
Rollback
A return to the previous version, to stop a problem quickly.
Secret
A password, an API key, or another value that gives access to a system.
Service level objective
A measurable target for a service, for example 99.9% availability each month.
