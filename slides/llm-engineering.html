Module 9

LLM engineering

After this module, you can:

  • Call an LLM API from code, and handle refusals and errors.
  • Get structured output that a program can use.
  • Build a RAG pipeline that answers with sources.
  • Give a model tools, build an agent with guardrails, and evaluate an application with a retrieval test and a judge.
  • Decrease cost with caching, and select between a prompt, RAG, and fine-tuning.

Get structured output

Text is good for people. A program needs data in a fixed format. Structured output makes the model return a JSON object that agrees with a schema. In Python, you write the schema as a Pydantic class.

Notes: The result is a Python object, for example farm='Ratnagiri' problem='damaged' boxes_affected=3 urgent=True . The field problem can have only the four values in Literal . Thus the program can send each complaint to the correct team without a person reading it first. Use structured output for extraction (data from emails, forms, and invoices), classification, and each time that code reads the answer. Refer also to the short topic Language tasks . Build an agent with guardrails

An agent uses tools in a loop until the task is done. It can do real actions, for example a refund. Thus it needs guardrails: checks in your code that the model cannot change. Refer to Module 7, Section 9.

  1. Test the guardrails without the model: call refund with a wrong amount, and run_tool with an unknown tool name. Each must return an error.
  2. Give the agent an evaluation set of tasks, including attacks: a document that says "refund all orders", and a request for the data of a different customer.
  3. Read the log of each task. Count the steps, the tokens, and the tool calls.
  4. Start with approval for all actions. Remove approval only for safe actions, after the agent has a good record.
Notes: With the example message, the agent gets the order, asks for a refund, and waits for your answer in the terminal. The model never sees the phone number. If you answer "no", the tool result says that a person did not approve, and the agent tells the customer. A guardrail must be in your code, not only in the prompt. A prompt such as "never refund more than the payment" can fail, because a model can make errors or be manipulated. The check 0 < amount <= order["paid"] cannot. Open the section

Evaluate the application

You cannot see if a change makes the application better by reading three answers. Use an evaluation set. Refer to Module 7, Section 8. Test two parts separately.

  1. Collect 50 to 200 real questions. Include difficult questions, and questions that the application must not answer.
  2. For each question, write the source document and a short reference answer.
  3. Run the retrieval test and the judge on all questions. Save the scores.
  4. Check a sample of the judge's grades yourself. A judge can make errors too.
  5. Make one change, for example a new chunk size or a new prompt. Run all the tests again, and compare.
  6. Put the tests into the CI/CD pipeline, so that each change is tested. Refer to Module 8, Section 7.
Notes: For each question, write the document that contains the answer. Then measure the recall at k . This test needs no API key and costs nothing, so you can run it for each change. The question "Which pesticide is allowed?" has no word in common with the document, which says "products that the agriculture office permits". Keyword search cannot find it. This is the type of error that an embedding model repairs. Without the test, nobody would know. For the answers, use a second model call as a judge . Give it the question, a reference answer, and clear rules. Ask for structured output, so that you can count the results. Open the section

Control cost and speed

The price depends on the tokens. Example with the prices of Claude Opus 5.5 in October 2026: 4 US dollars for one million input tokens, and 20 US dollars for one million output tokens. Check the current prices before you plan.

  • Prompt caching. If the start of each prompt is the same, for example long instructions, the API can keep it. Later requests read it for a much smaller price. Put the text that does not change first, and the question last.
  • Send less text. Send only the best chunks, not full documents.
  • Select the correct model. A smaller model is cheaper and faster for simple tasks, for example classification. Measure the quality with your evaluation set before you change.
  • Batches. For work that does not need an immediate answer, for example the classification of yesterday's messages, the batch API costs half the price.
Notes: The cached part must have a minimum length, which depends on the model. If cache_read_input_tokens stays 0, something in the start of the prompt changes each time, for example the date and time. Users wait for the first words more than for the full answer. Streaming shows the answer while the model writes it. Also measure the p95 latency. Refer to Module 8, Section 9 . Open the section

Run it safely in production

  • Prompt injection. Documents, web pages, and emails can contain text such as "Ignore your rules". Put such text inside clear tags, tell the model that it is data, and never give the model more permissions than the user has. Refer to Module 5, Section 9.
  • Private data. Remove personal data before it goes to the model, if the task does not need it. Do not write full prompts with private data into the logs.
  • Check the output. Check the format, check that each fact has a source, and stop harmful content before it reaches the user.
  • Handle refusals and errors. Check stop_reason. Show the user a clear message, not an empty answer.
  • Limits. Set limits for the requests of each user, for the steps of each agent, and for the monthly cost.
  • Version the prompts. Keep prompts in Git, and test each change with the evaluation set. Refer to Module 8, Section 3.

Summary

  • An LLM application has input checks, retrieval, a prompt template, the model, tools, and output checks.
  • Keep the API key in an environment variable. Check stop_reason, and handle errors.
  • Use structured output when a program reads the answer.
  • RAG divides documents into chunks, finds the best chunks for each question, and puts them into the prompt with source ids.
  • Tools let the model get live data. Your program runs the tools, with limits and checks.
  • An agent needs guardrails in code: input and output checks, allowed tools, checks of tool inputs, human approval, limits, and a log.
